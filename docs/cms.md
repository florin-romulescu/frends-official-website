# Content from WordPress (headless)

The site is statically generated by Astro. Page copy lives in code (`src/data/i18n/ro.json`); content that changes often comes from a self-hosted WordPress, read over the REST API **at build time**. Visitors never touch WordPress except for image files.

| In WordPress | On the site |
|---|---|
| Posts | `/blog`, `/blog/<slug>` |
| Events (`Evenimente`) | the carousel on the home page, `/evenimente/<slug>` |
| Projects (`Proiecte`) | `/proiecte`, `/proiecte/<slug>` |
| Partners (`Parteneri`) | the "Partenerii noștri" section on the home page |
| Site settings (`Setări site`) | contact, address, social links, the "Fii voluntar" link (header, footer, buttons) |

## The backend (`wordpress/`)

Everything needed to stand WordPress up from scratch is in the repo:

```
wordpress/
├─ docker-compose.yml          WordPress + MariaDB (+ Caddy with automatic TLS, `prod` profile)
├─ .env.example                credentials, domain, build hook
├─ Caddyfile                   reverse proxy; blocks xmlrpc and sensitive files
├─ setup.sh                    WP-CLI bootstrap: Romanian locale, permalinks, ACF, theme, the "Setări site" entry
├─ themes/frends-headless/     bare theme (redirects to the site) + acf-json/ (field schema, versioned)
├─ mu-plugins/frends-headless.php   post types, build hook, hardening
└─ backup/                     backup.sh / restore.sh with restic, cron example
```

### Running locally

```sh
cd wordpress
cp .env.example .env            # WP_HOME=http://localhost:8080, local passwords
docker compose up -d
./setup.sh                      # idempotent; safe to rerun
```

Admin: <http://localhost:8080/wp-admin> (user/password from `.env`). In the project root, `.env` holds `WP_API_URL=http://localhost:8080`; then `pnpm dev`.

`themes/frends-headless/acf-json` is bind-mounted from the repo: editing field groups in the ACF UI rewrites the JSON files locally — commit them. On Linux, give the `www-data` user (uid 33) write access: `sudo chown -R 33:33 wordpress/themes/frends-headless/acf-json`.

### Production (VPS)

1. A small VPS with Docker + Compose, firewall open only on 22/80/443, DNS `cms.frends.ro` → the server IP.
2. `git clone` into `/opt/frends-website`, `cd wordpress`, `cp .env.example .env` and fill in: passwords, `CMS_DOMAIN=cms.frends.ro`, `WP_HOME=https://cms.frends.ro`, `ASTRO_SITE_URL=https://frends.ro`, `BUILD_HOOK_URL` (see below).
3. `docker compose --profile prod up -d` — Caddy obtains the certificate; then `./setup.sh`.
4. Updates: `git pull && docker compose --profile prod pull && docker compose --profile prod up -d`, once a month. WordPress applies minor core updates on its own.
5. Cron: `backup/crontab.example` holds the nightly backup and a daily build trigger (so event statuses roll over even without edits).
6. Backups: `cp backup/.env.backup.example backup/.env.backup`, fill in the restic repository (S3-compatible: Backblaze B2, Hetzner Storage Box), run `restic init`, then add the cron job from `backup/crontab.example`. Restore with `./backup/restore.sh [snapshot]`.

The only data that cannot be regenerated is the database and `wp-content/uploads`. Everything else (theme, plugin, ACF schema) is in git.

### Automatic builds on publish

`mu-plugins/frends-headless.php` POSTs to `BUILD_HOOK_URL` whenever a post / event / project / partner / the settings entry is published, updated or deleted. Create a build hook in Netlify (Site configuration → Build & deploy → Build hooks), Vercel (Settings → Git → Deploy Hooks) or Cloudflare Pages (Settings → Builds → Deploy hooks), put the URL in `.env`, and run `docker compose up -d` to apply it. In the host's build settings, define `WP_API_URL=https://cms.frends.ro`.

## Editing content

Every type requires a **featured image** — the build stops with a clear message if one is missing. Also fill in "Text alternativ pentru imaginea principală" (or the file's alt text in Media).

- **Event**: title, excerpt (shown on the card), content (detail page), *Data de început* and optional *Data de sfârșit*. The status badge and the period label are derived from the dates at build time: before the start → "Înregistrări deschise", between start and end → "În desfășurare", after the end → "Terminat" (a missing end date means a one-day event). Because statuses depend on the calendar, the cron in `backup/crontab.example` also triggers one build per day.
- **Project**: title, *Rezumat*, *An*, *Proiect principal* (listed first), content.
- **Post**: title, excerpt, content, featured image. The publish date is shown on the card.
- **Partner**: title = name, featured image = logo, *Site*, *Ordine* (ascending).
- **Site settings**: a single entry ("Setări site"). One address line per row; the "Fii voluntar" link may be external (Google Forms) or a page on the site (`/fii-voluntar`).

The WordPress slug becomes the page URL (`/evenimente/<slug>`). Drafts and private posts never reach the site.

## How content reaches the code

- `src/lib/wp.ts` — the REST client (paginates automatically), featured image → `ResolvedImage` (srcset from the sizes WordPress generates), HTML cleanup.
- `src/content.config.ts` — the `events`, `projects`, `blog`, `partners`, `settings` collections with zod schemas. Components use `getCollection()` / `getEntry('settings', 'site')`.
- `src/data/site.ts` — `getSite()` merges the WordPress settings with the navigation from `src/data/site.json` (which stays in code).

- `src/integrations/wp-refresh.ts` — dev only: polls WordPress every 10 s (`WP_REFRESH_INTERVAL` in ms to change it) and refreshes the collections when something was modified, so edits show up in `astro dev` without a restart. Production builds fetch once; the build hook handles redeploys.
